Title: Visits store with a status summary, shared with other front ends through a host bridge

Story: As the front-desk team, I want the clinic app to keep all visits and a count per status in one shared place, so that other front-end apps loaded alongside it (the front-desk panel, story PC-104) can show the same numbers without calling the API themselves.

**Requires a new or changed contract from:** petclinic-rest-api

Expected behaviour:
- The backend returns every visit with a `status` (`GET /api/visits`; the allowed values are the `VisitStatus` enum in the attached `openapi.yml`: `SCHEDULED`, `COMPLETED`, `CANCELLED`). The app already has a `VisitStatus` type (`src/app/visits/visit-status.ts`) and `VisitService.getVisits()`; reuse both.
- Add an NgRx feature store for visits under `src/app/store/visits/`, one file per concern: `visits.actions.ts`, `visits.reducer.ts` (with the state interface, feature key `visits`), `visits.effects.ts`, `visits.selectors.ts`. The root store is already provided in `src/main.ts`; register the feature state and effects from `VisitsModule` (`src/app/visits/visits.module.ts`).
- State: the list of visits, a loading flag, and an error message (null when there is none).
- Actions: load visits; load succeeded (with the visits); load failed (with an error message).
- The effect calls `VisitService.getVisits()` on "load visits" and dispatches success or failure.
- Selectors: all visits; loading; error; and the **count per status**: an object with exactly the keys `SCHEDULED`, `COMPLETED`, `CANCELLED` and a number for each (0 when there are none), plus `notSet` for visits with no status or an empty one.
- The app dispatches "load visits" once when it starts (`AppComponent`).
- **Host bridge:** add `src/app/store/visits/visits-bridge.ts`. It publishes the visits state to other front ends on the page: every time the state changes it sets `window.petclinicHost.visits` to `{ visits, statusCounts, loading, error }` and dispatches a browser event named `petclinic-host:visits` with the same object as `detail`. Export the TypeScript interface of that object (`VisitsBridgeState`) and the event name as a constant from the same file. Start the bridge once at app start.
- No visible change to existing pages.

Acceptance criteria:
- AC1: `src/app/store/visits/` contains `visits.actions.ts`, `visits.reducer.ts`, `visits.effects.ts`, `visits.selectors.ts` and `visits-bridge.ts`, and the feature is registered under the key `visits`.
- AC2: Dispatching "load visits" calls `VisitService.getVisits()` once; on success the state holds the returned visits with `loading` false and `error` null; on failure `loading` is false and `error` holds a message.
- AC3: The status-count selector returns `{ SCHEDULED, COMPLETED, CANCELLED, notSet }` with correct numbers; a visit with no status, null, an empty string or only spaces counts as `notSet`; a value outside the three is also counted as `notSet` and nothing breaks.
- AC4: The status values come from the existing `VisitStatus` type, not new string literals.
- AC5: After the app starts and the visits load, `window.petclinicHost.visits` holds `{ visits, statusCounts, loading: false, error: null }` and a `petclinic-host:visits` event has been dispatched with the same object; `VisitsBridgeState` and the event-name constant are exported from `visits-bridge.ts`.
- AC6: Existing pages (owners, pets, visits, vets) behave exactly as before.
- AC7: `npm install … && npx ng build` passes.
-  AC8: Load behaviour. Initial state (also the first value published on the bridge) is visits empty, loading false, error null. "Load visits" sets loading true and error null. A failed load sets loading false and error to the fixed text "Could not load visits.", and keeps the visits from the last successful load. If "load visits" is dispatched while a load is in flight, the in-flight request is cancelled and only the latest result is applied (switchMap).
- AC9: Failure path. `VisitService.getVisits()` already re-throws HTTP errors (`HttpErrorHandler.handleError` returns `throwError(message)`; its default-result argument is unused), so the effect catches the error and dispatches "load failed". `VisitService` and `error.service.ts` stay unchanged. The server's message is never stored or published.
- AC10: Bridge payload. The store keeps visits as the API returns them (per the attached contract: no nested pet object). The bridge publishes only `id`, `date`, `status` and `petId` for each visit, never `description`.

Note: 
The store keeps visits as the API returns them (per the attached contract: no nested pet object). The bridge publishes only `id`, `date`, `status` and `petId` for each visit, never `description`. On failure, `error` is the fixed text "Could not load visits." in both the store and the bridge, and never contains server response content.
  
In scope:
- `src/app/store/visits/*` (new), `src/app/visits/visits.module.ts` (register the feature), `src/app/app.component.ts` (dispatch on start, start the bridge).

Out of scope: `package.json` and `src/main.ts` (NgRx is already installed and the root store provided), any UI change, the front-desk panel (story PC-104), backend changes, unit tests (this repo runs build-only).

Attachments:
- `stories/PC-103/openapi.yml` — petclinic-rest-api's OpenAPI file after PC-101, copied as it is (from its `harness-metrics` branch, `contracts/PC-101/`).
